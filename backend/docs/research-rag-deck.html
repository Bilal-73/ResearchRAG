Starting point01
Where this began

A medical RAG that could not be measured

Ten diabetes papers, a Streamlit UI, and an evaluation that proved nothing. Three problems, each fatal in a different way.

Problem 01

The evaluation was circular

Ground truth was LLM-generated from the same chunks the retriever returned. A good score only proved the pipeline agreed with itself.

self-referential by construction
Problem 02

The corpus was one paper

Ten PDFs on disk, one actually indexed. Any retrieval metric was meaningless because there was nothing to retrieve against.

recall@k = 1.0 means nothing at n=1
Problem 03

Streamlit is not an interface

No typed contract, no status codes, nothing another program could call. A demo, not a system.

no API surface
The pivot

Rebuilding around the Open RAG Benchmark fixed all three at once — it brings its own questions, its own reference answers, and relevance judgments at section granularity. That last detail drove most of the architecture that follows.

Design consequence

Because the benchmark judges (doc_id, section_id), a chunk may never span two sections and every chunk records its section_id. Without that you cannot distinguish "found the right paper" from "found the right paragraph" — and those have different fixes.

Ingestion05
Read → chunk → embed → upsert

Chunking decisions that set the score ceiling

Rule 01

Never span two sections

The qrels are (doc, section) pairs. A chunk straddling a boundary makes a hit unattributable.

Rule 02

Contextualise every chunk

Prefixed with title › section heading. "The error drops by 38%" alone is unretrievable.

Rule 03

Tables and figures stand alone

With their caption and referencing sentence. 32% of queries need them — folding them into prose caps recall.

Rule 04

Pack with overlap

Token-bounded paragraphs, one repeated between chunks, so a fact split across a boundary survives.

Resumability

The manifest is the resume log

Asymmetric by design

Low confidence → search

An uncertain intent collapses to new_question. Routing a real question to grounded retrieval is harmless; routing it to chit-chat loses the answer.

Cheap first

Rules before models

"hello" routes by rule with zero LLM calls. The planner asks a regex whether a question might be compound before paying for an LLM.

Bounded

The loop cannot spin

Corrective retrieval is capped by MAX_RETRIEVAL_RETRIES, with a LangGraph recursion limit as a second backstop.

Guardrails07

The API cannot claim a guardrail it is not running

GET /v1/guardrails renders from a single registry in code, with each enabled flag read from live settings. The page and the behaviour cannot drift apart.

Real bug found

The injection scanner treated "ignore … prior … context" as an attack — ordinary ML-paper prose. That rule also scans retrieved chunks, so it was silently dropping legitimate evidence from the answer.

Real bug found

1234.5678 matched the arXiv-id pattern, so the reference check would strip legitimate decimals out of answers. The month is now constrained to 01–12.

Evaluation09
Three stages

Retrieval, answer quality, and refusal — scored separately

Stage 01

Retrieval

Recall@k, MRR, NDCG at document and section level, split by query type and modality. Judge-free — the most trustworthy signal in the whole suite.

no generation, no judging
Stage 02

Answer quality · RAGAS

Faithfulness, answer relevancy, context precision, context recall. Judge models wired to the project's own Azure deployments.

--judge builtin swaps in a dependency-free judge
Stage 03

Refusal

Real benchmark questions whose gold paper was deliberately left unindexed. The question is well-formed; the evidence genuinely is not there.

anything but a refusal is a hallucination
Only score what is indexed

Queries whose gold document was never ingested are dropped, and the count reported. Scoring them would measure the size of the ingestion budget, not the quality of the retriever. At 50 papers: 373 scored, 2,672 dropped.

Stratified sampling, fixed seed

A random 100-query sample is ~63% text-only, so multimodal regressions hide in the noise. Sampling proportionally across (type, source) keeps every slice represented and makes two runs comparable.

Every multimodal slice has lower MRR than text. The right section is found, but ranked lower — a reranking problem, not a retrieval problem.

RAGAS11
ragas 0.3.9 · wired to Azure

Two things the documentation will not tell you

Gotcha 01

The deprecated wrapper is the one that works

RAGAS deprecates LangchainLLMWrapper in favour of llm_factory. But the object llm_factory returns has no agenerate_prompt — which is exactly what the metrics call.

Result: every score came back nan. The deprecated wrapper stays, its warning silenced, with the reason recorded in the code.

Gotcha 02

It will not use your Azure setup on its own

ragas.evaluate() reaches for a plain OPENAI_API_KEY unless handed judge models explicitly.

Column names also changed in 0.2+: samples are user_input / response / retrieved_contexts / reference, and the dataset is an EvaluationDataset, not a HuggingFace Dataset.

The finding that matters

Relevancy 0.735 is not an answer-quality problem — it is over-refusal. 12% of answerable questions got "This is not reported in the retrieved context", and RAGAS scores a refusal 0. Excluding refusals: relevancy 0.848, faithfulness 0.935.

Diagnosis

Retrieval finds it; the generator won't use it

The right section is retrieved 89.8% of the time, but the generator declines on roughly 1 in 8 answerable questions.

target: context grader or prompt strictness
Caveat 01

Refusal accuracy is a lower bound

The negative set is "gold paper not indexed" — not the same as unanswerable. One question's gold paper was excluded but another indexed paper answered it correctly.

marked as a hallucination for being right
Caveat 02

Null is not zero

context_precision returned NaN on 11 of 60 rows. Averages skip them; n_scored reports how many contributed. Averaging NaN as 0 would invent a quality problem.

check n_scored before comparing runs
Finding13
Surfaced by the UI, not by the test suite

The judge was punishing the system for admitting uncertainty

Symptom

A good answer scored 0.00 relevancy

The first scored answer in the browser showed relevancy 0.00 on an answer that was clearly correct and well-cited.

Cause

RAGAS scores hedged text as "noncommittal" = 0

The system appends ⚠️ statements may not be fully supported… to uncertain answers — and that warning was being fed to the judge along with the answer.

Fix

Strip annotations before judging

Guardrail warnings are annotations about the answer, not part of it. The user still sees the warning; the judge sees the model's answer.

Same answer, same questionreproduced
with our warning appended0.00
warning stripped0.55
faithfulness — with warning0.50
faithfulness — stripped0.67
live re-check after fix0.48

Any metric applied to a system that admits uncertainty deserves the same scrutiny. An honest system can score worse than a confident wrong one.

Safety properties

Scoring can never break an answer

A judge failure degrades to null scores with a reason, never a failed request. The judge is built once per process, on first use. RAGAS runs in a worker thread so it never blocks the event loop.

What is not scored

Non-grounded turns say why

Chit-chat, refusals and blocked turns have no retrieved context to score against — they return an explanation instead of a number.

verified: 1.00 / 1.00 on a clean question · 0.00 faithfulness on a planted hallucination
Rendering rule

A null score renders as a dash with its reason, never as zero. The backend distinguishes "scored low" from "could not be computed" — collapsing those two would turn a measurement outage into a fake quality problem.

Before anyone exposes this

API_KEYS is empty (the API is open), CORS_ORIGINS=*, and rate limiting is per-process. /health reports auth: degraded so it is visible rather than silent — but it is still open.

Trust the judge-free numbers more

Both judges run on the same model family as the generator, so neither is an independent opinion. The retrieval metrics have no judge in the loop — treat RAGAS as a relative signal between runs, not an absolute truth.
